## Reading the DB

```python
sqlite3.connect(f"file:{db}?mode=ro&immutable=1", uri=True)
```

- `immutable=1` skips `-shm`/`-wal` and locking, so it works on the S0-4 frozen route (`codegraph.db` bind-mounted `:ro`).
  `sqlite3 -readonly` on the pristine copy fails with `unable to open database file (14)`.
- Safe only because the DB is frozen for the whole run. F must never open a DB that CodeGraph is writing.
- SHA-256 before and after every script run: unchanged on Django, sympy, transformers and home-assistant.

- Confidence is a **label of the resolver strategy**, not a probability. Example: `instance-method` matches by a shared
  word get 0.65 (`src/resolution/name-matcher.ts:25369`); exact-name guesses get 0.7 or 0.4 by path proximity
  (`name-matcher.ts:6444`). 73% of non-`contains` edges are 0.9.
- So `c(e)` in §13.2 mostly separates "guessed" edges (0.4/0.65/0.7) from the rest. That is still useful, but small; the
  `c(e) = 1` ablation should stay.

**Consequence for §13.2 τ groups (Python):** hierarchy = `extends` only; type use = `instantiates` + `decorates`;
reference = `imports` + `references`; containment = `contains`. Four fitted τ values still apply, but `decorates`
is tiny (0.3% of edges), so the type-use τ is effectively an `instantiates` weight.

## PPR latency

Method (`scripts/s0_5_schema.py`): load node IDs and edges once; forward weight `c(e)`, reverse weight `ρ·c(e)`, every
τ = 1, ρ = 0.5; row-normalise; power iteration `π = α·s + (1−α)·Pᵀπ` with α = 0.25, L1 tolerance 1e-6, dangling mass
returned to `s`. Each query: 50 random seed nodes with RRF weights `1/(60 + rank)`, PPR, hub correction
(β = 0.5, global PageRank computed once), top 200. 100 queries per graph, seed 0. numpy 2.5, one thread, no scipy.
macOS arm64 (M-series), Python 3.12.

| Repo (commit) | `.py` files | Nodes | Edges | DB | Index time | Load | Global PR | PPR p50 | **PPR p95** | max | Iterations |
|---|---|---|---|---|---|---|---|---|---|---|---|
| django `1860f0a3f4` | 3,031 | 62,854 | 194,344 | 185 MB | 24 s | 0.5 s | 93 ms | 71 ms | **103 ms** | 137 ms | 34–43 |
| sympy `6452b07714` | 1,610 | 59,966 | 399,095 | 281 MB | 37 s | 0.8 s | 155 ms | 142 ms | **170 ms** | 223 ms | 35–40 |
| transformers `cdb75de4ad` | 5,043 | 139,174 | 375,558 | 514 MB | 112 s | 0.6 s | 91 ms | 91 ms | **99 ms** | 222 ms | 33–38 |
| home-assistant/core `376e7e9618` | 20,399 | 410,968 | 1,186,571 | 1.29 GB | 249 s | 1.9 s | 486 ms | 316 ms | **351 ms** | 462 ms | 34–39 |

- Cost grows roughly linearly with edges: p50 is 0.24–0.37 ms per 1k edges per query at ~37 iterations, so the
  500 ms p95 limit sits around 1.5M edges with this code. π sums to 1 within 1e-14.
- **azure-sdk-for-python: index failed.** `init` exited 1 during "Resolving refs" after 425 s with no error text
  (Docker Desktop VM: 8 GB). Cause not confirmed; memory is the likely one. The partial DB has only `contains`,
  `imports`, `references` and `extends` edges, with 3.29M refs still unresolved, so the full graph would be several
  million edges. Even partial, PPR p95 is 457 ms. A full graph would be well over 500 ms with this code.
  **F0 can't index this repo either on this machine**, so it's unusable for both arms as things stand.
- **Largest pool graph.** All 364 pool repos measured (`scripts/s0_5_repo_sizes.py`: `.py` files and bytes at
  each repo's newest task `base_commit`, GitHub tree API; 0 errors). The hand-picked repos are the top three:
  azure-sdk-for-python 506 MB of `.py` (tree truncated, so a lower bound), home-assistant/core 80 MB, transformers
  69 MB. Next is cpython at 32 MB (1 task). home-assistant at its task commit is 57% of the HEAD tree indexed above
  (141 MB), so its task graphs are smaller than the measured 1.19M edges. Measured edges per `.py` MB: 4.7k
  (transformers) to 14.1k (sympy); at the worst ratio, every repo except azure stays under ~1.1M edges.
- Index time is Docker Desktop on macOS; shallow clones at HEAD on 2026-11-05 (the commit doesn't matter for timing).
- **Headroom if needed:** float32 arrays, edges pre-sorted by target, or warm-starting from the global vector. Not
  needed at these sizes. A cap on repo size in `test_core` is the other lever.

## Reproduce

```bash
C=${EVALH_CACHE:-$HOME/evalh-cache}
for repo in sympy/sympy huggingface/transformers home-assistant/core; do
  n=${repo//\//__}
  git clone -q --bare --depth 1 https://github.com/$repo.git $C/repos/$n.git
  sha=$(git -C $C/repos/$n.git rev-parse --short=10 HEAD); T=$C/trees/$n-$sha; mkdir -p $T
  git -C $C/repos/$n.git archive HEAD | tar -x -C $T                    # clean tree, no .git
  docker run --name cg-index-$n --rm --network none -v $T:/repo evalh/codegraph:f72c9d2 init -y /repo
  uv run python scripts/s0_5_schema.py $T/.codegraph/codegraph.db       # exit 0 = DB unchanged
done
uv run python scripts/s0_5_schema.py $C/django-1860f0a3f4.codegraph.pristine/codegraph.db
uv run python scripts/s0_5_repo_sizes.py   # all pool repos' .py size via GitHub API (gh login), ~80 s
```
